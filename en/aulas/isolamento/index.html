Lesson 5 · 20 min

Isolation: worktrees and sandboxes

Two agents in the same checkout don't throw an error: one silently erases the other's work. A worktree gives each one its own copy and turns the silent loss into a visible conflict at merge time. A sandbox does the same with permissions: the reviewer reads, but doesn't write. In this lesson you prove both without spending quota.

Start the lesson

In this lesson you will

  1. 1The lost write: two agents, one file, no error
  2. 2Worktree by hand, in claude --worktree, in a subagent, and in Codex
  3. 3Codex read-only and workspace-write sandboxes, tested
  4. 4The merge conflict as a good sign

Goal: give each agent that writes its own worktree and each reviewer a read-only sandbox, and prove the difference.

02 · Rehearsal: the lost write and the worktree

A disposable repository and two fake agents that read, wait 2 s, and write the whole file.

Terminal · no-quota rehearsal
E=${TMPDIR:-/tmp}/ensaio-multi/wt; rm -rf $E && mkdir -p $E && cd $E
git init -q repo && cd repo && git config user.name ensaio && git config user.email ensaio@local
printf 'versao = 1\nnome = treino\ncor = azul\n' > config.txt && git add -A && git commit -qm base
# um "agente" lê o arquivo, pensa 2 s e grava o arquivo inteiro (como a ferramenta Write)
agente() { c=$(cat "$1/config.txt"); sleep 2; printf '%s\n' "$c" | sed "$2" > "$1/config.txt"; echo "$3 gravou"; }

echo "## A) dois agentes no MESMO checkout"
agente . 's/azul/verde/' A & agente . 's/versao = 1/versao = 2/' B & wait
cat config.txt
git checkout -q config.txt

echo "## B) um worktree para cada agente"
git worktree add -q ../wt-a -b agente-a && git worktree add -q ../wt-b -b agente-b
agente ../wt-a 's/azul/verde/' A & agente ../wt-b 's/versao = 1/versao = 2/' B & wait
git -C ../wt-a commit -qam "A: cor" && git -C ../wt-b commit -qam "B: versão"
git merge -q agente-a && git merge -q --no-edit agente-b && cat config.txt
git worktree list | wc -l
Example from the repository
## A) dois agentes no MESMO checkout
B gravou
A gravou
versao = 1
nome = treino
cor = verde
## B) um worktree para cada agente
A gravou
B gravou
Auto-merging config.txt
versao = 2
nome = treino
cor = verde
3

In A, both said "gravou" and version 2 vanished. In B, both changes went in. The order of "A gravou" and "B gravou" varies from one round to the next; the result doesn't.

Two worktrees changing the SAME line (cor roxo × cor preto), captured in the same repository:

Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
Automatic merge failed; fix conflicts and then commit the result.
saída: 1

In a single checkout, this would be a silent loss. Here git stops and shows it. The one who resolves it is the orchestrator (or you), not one of the two agents.

03 · Worktree in the tools

Claude Code 2.1.303 and Codex CLI 0.163.0, per the docs read on 10/19/2026.

1. claude --worktree

claude --worktree [name] creates the worktree in .claude/worktrees/[name] and opens the session there. It needs at least one commit and, in interactive mode, the folder marked as trusted (run claude once in it).

Files ignored by git, like .env, don't go to the worktree; list them in a .worktreeinclude at the root to copy them.

GotchaHooks using ${CLAUDE_PROJECT_DIR} keep running in the main checkout; it's the hook's cwd field that follows the worktree.

2. Subagent

In the frontmatter, isolation: worktree gives the subagent a temporary worktree, which disappears on its own if it changes nothing.

Heads up: the branch starts from the default branch, not from your session's HEAD. Anything you haven't committed isn't there.

3. Sessions and teams

A background session (claude --bg) enters a worktree before editing. Agent teams don't isolate: split the files by owner.

A periodic cleanup removes worktrees created by Claude that are older than cleanupPeriodDays and hold no work.

4. Codex

codex exec --worktree "[pedido]" runs in a managed worktree (it doesn't combine with resume or --ephemeral). In the TUI, /worktree.

Sandbox: -s read-only for those who only review, -s workspace-write for those who execute. The docs ask you to avoid --dangerously-bypass-approvals-and-sandbox outside a dedicated VM.

04 · Sandbox per role, tested without a model

codex sandbox runs any command under the same rules Codex uses for its own. It doesn't call a model.

Terminal · no-quota rehearsal
E=${TMPDIR:-/tmp}/ensaio-multi/sbx; rm -rf $E && mkdir -p $E && cd $E
codex sandbox -c sandbox_mode=read-only -- bash -c 'echo x > a.txt 2>/dev/null && echo "read-only: gravou" || echo "read-only: bloqueado na pasta"'
codex sandbox -c sandbox_mode=workspace-write -- bash -c 'echo x > b.txt && echo "workspace-write: gravou na pasta"; echo x > ~/fora-sbx.txt 2>/dev/null && echo "gravou fora" || echo "workspace-write: bloqueado fora da pasta"'
ls; ls ~/fora-sbx.txt 2>&1 | tail -1
Terminal · a real worktree in the practice project
# terminal 1: opens the session already inside the worktree (no need to ask for anything)
cd ~/treino-multi && claude --worktree treino-a

# terminal 2, with the session open:
cd ~/treino-multi && git worktree list | grep -c ".claude/worktrees/treino-a"
git branch --list worktree-treino-a

# terminal 1: /exit (worktree with no changes: choose remove, if it asks). Then:
git worktree list | wc -l
Example from the repository
bash: line 1: a.txt: Read-only file system
read-only: bloqueado na pasta
workspace-write: gravou na pasta
bash: line 1: ~/fora-sbx.txt: Read-only file system
workspace-write: bloqueado fora da pasta
b.txt
ls: cannot access '~/fora-sbx.txt': No such file or directory

Edited on purpose: your home folder path shows up as ~. The read-only run didn't write even inside the folder; workspace-write wrote b.txt and was blocked outside.

A worktree starts from a commit. In a freshly created git init, claude --worktree exits before calling the model (captured with Claude Code 2.1.303):

Error creating worktree: Failed to resolve base branch "HEAD": git rev-parse returned no commit for HEAD (for example in a new repository, or on a branch without a commit yet), so Claude Code has nothing to base a worktree on. (…)
saída: 1

Make a commit and run it again.

07 · In three sentences

A single checkout losesTwo agents writing the same file: the last one wins and nobody is told.
One worktree per writerEach agent that writes gets its own copy and branch; the merge joins them or shows the conflict.
Sandbox per roleReviewer in read-only, executor in workspace-write; full access only in a dedicated VM.
